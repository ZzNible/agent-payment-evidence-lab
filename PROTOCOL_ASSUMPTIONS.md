# Protocol Assumptions

This document defines the assumptions under which the laboratory's reports are meaningful. If an assumption changes, the result may need to be regenerated or reinterpreted.

## Pinned protocol surface

The initial harness pins these x402 packages at `2.19.0`:

- `@x402/core`
- `@x402/express`
- `@x402/fetch`
- `@x402/evm`

The version pin is evidentiary, not cosmetic. The laboratory demonstrates behavior of a particular implementation. It does not claim that all x402 integrations, facilitators, framework adapters, payment schemes, or future releases behave identically.

This declared-version boundary is fail-closed: the v0.1 evidence-bundle schema accepts only `protocol: "x402"` and `protocolVersion: "2.19.0"`. Evidence labeled as another x402 version is rejected at document validation; the lab does not silently apply 2.19.0 semantics to it. The label is still a statement in the bundle, not independent proof that imported evidence was generated by that implementation.

In the inspected `@x402/express` 2.19.0 implementation:

1. the middleware verifies the presented payment before running the protected handler;
2. it buffers the handler response;
3. it does not call settlement when the handler returns status `>= 400`;
4. it dispatches a cancellation when a verified request fails or the handler throws;
5. any handler status below `400` may proceed to settlement before the buffered response is sent, including `202` and potentially `3xx`; the middleware does not evaluate response-body semantics or later work.

This protects the narrow synchronous handler boundary. It does not make later asynchronous work part of the same settlement condition.

## What “settled” means in this repository

In generated lab evidence, `settled` means:

> the pinned middleware called the configured settlement boundary, and the synthetic facilitator returned the configured successful result.

It does **not** mean:

- assets moved on a production network;
- a transaction reached legal or economic finality;
- the payer's account was charged;
- the payee can spend the proceeds;
- the response body satisfied an obligation;
- an asynchronous job later completed.

A production adapter would need a stronger and explicitly documented definition, including network, confirmation, finality, and failure semantics.

## Synthetic facilitator boundary

The local facilitator is a deterministic test double. It is used so the full scenario suite can run without credentials, funds, RPC endpoints, or external services.

The harness uses the production x402 middleware lifecycle around that boundary, but the facilitator itself is not production evidence. It may:

- accept a controlled fixture payment;
- return controlled verification and settlement results;
- record method calls and lifecycle events;
- expose deterministic failure modes for tests.

It does not:

- perform real cryptographic or economic verification unless a scenario explicitly states otherwise;
- connect to an asset ledger;
- model liquidity, chain reorganization, facilitator insolvency, or network delay;
- assert that a real facilitator would accept the same request.

Any report derived from it must identify the trust profile as a local fixture and retain the associated limitation.

The payment-verification verifier accepts only signed fixture content with `mode: "local-recording-double"` and `realNetworkVerification: false`. The settlement verifier likewise accepts only `mode: "local-recording-double"` with `realFundsMoved: false`. A valid signature over a different profile does not become production payment proof.

The facilitator's payment-verification and settlement artifacts are signed by the ephemeral identity precommitted for `local-recording-facilitator`. Signing authenticates the fixture attestation and its canonical envelope; it does not turn the recording double into a production facilitator. Separately, the x402 client creates a local EVM key and signs an EIP-3009 fixture authorization, but the recording double does not cryptographically or economically verify it and no funded transaction is submitted.

## Three-document model

The laboratory separates intent, observation, and conclusion:

1. **Verification plan** — predicates and trust assumptions committed before execution;
2. **Evidence bundle** — observed artifacts, provenance declarations, digests, and correlation data;
3. **Verification report** — claim results derived from the exact plan and bundle.

The schemas are versioned independently:

- `apel.verification-plan/0.1`
- `apel.evidence-bundle/0.1`
- `apel.verification-report/0.1`

The report contains digests of its exact canonical inputs. This makes later semantic modification detectable when the same canonicalization and digest rules are applied. The commitment is to the canonical JSON value, not to incidental source-file whitespace or transport bytes, and it does not prove that the content was true when created.

## Precommitment assumption

The model assumes that the plan, including relevant schemas and source rules, is committed before the outcome is known. Otherwise a party could redefine success after observing the result.

For a schema-based claim, the plan identifies both the schema artifact and the digest of its schema content. A mutable URL alone is not a precommitment. Artifact-consuming semantic claims identify the expected issuer explicitly in their parameters (`issuerId` or a role-specific issuer field), rather than trusting whichever issuer happens to be embedded in the bundle. The plan also commits the exact trust-context digest; changing source independence, authority, assumptions, or issuer-to-key bindings after execution causes the relevant claims to fail their commitment check.

The local lab can demonstrate digest consistency. It does not provide an external timestamping or publication service that proves when the commitment was made.

## Correlation assumption

Evidence is meaningful only when it is bound to the same interaction. The current model relies on explicit identifiers and digests, such as:

- `planId` and `bundleId`;
- `interactionId`;
- payment attempt or request identifiers where available;
- job identifiers for deferred work;
- resource and response digests;
- capture and issuance timestamps.

The current fixture enforces several claim-specific bindings in addition to the artifact envelope's `interactionId`:

- the payment payload's resource URL must equal `plan.subject.resource`;
- the signed HTTP capture's `resourceUrl` must equal that same plan resource;
- a source-statement claim declares an `interactionField`, whose signed content value must equal the plan interaction ID;
- a deferred-job artifact's job ID must equal the job ID in the signed HTTP capture.

Matching labels are not, by themselves, proof that two systems refer to the same real-world event. A production integration must explain who creates each identifier, whether either party can reuse it, and how it is propagated across boundaries.

In the present scenarios, the harness itself constructs the resource URL, injects artifact `interactionId` values, captures the HTTP `resourceUrl`, and creates the job identifier. The enforced bindings therefore prove internally signed fixture consistency, not independent end-to-end propagation across real systems. The settlement artifact also does not independently bind a resource or deferred job unless an explicit commitment is added.

## Time and replay assumptions

Timestamps are treated as statements by their issuing systems unless backed by a separately trusted time source. Local scenarios assume a coherent process clock for reproducibility.

A production trust profile should define:

- acceptable clock skew;
- freshness windows;
- nonce uniqueness;
- replay detection scope and retention;
- behavior when an external system changes state after capture.

An old, validly signed artifact can still be irrelevant to the current interaction.

## Provenance assumptions

Each artifact declares an issuer, role, and controller. Those fields are covered by the artifact digest and, for decisive fixture observations, by an Ed25519 signature over the canonical envelope. They become an authenticated fixture identity only when the applicable claim names the expected issuer and the precommitted trust context binds that issuer to the verifying public key. The declared controller remains a policy statement, not a cryptographically discovered organizational fact.

The model distinguishes:

- **authenticity:** did the expected key or channel issue the artifact?
- **integrity:** has the artifact changed?
- **independence:** is the source outside the material control of both parties?
- **authority:** did the plan designate the source as competent for this predicate?

A signature can support authenticity and integrity only when the signing key was already bound to the claimed issuer through the committed trust profile. A public key supplied solely inside the signed artifact is self-consistent but does not authenticate a named organization. Even with a valid key binding, a signature cannot establish organizational independence or contractual authority without further evidence.

The v0.1 trust context represents authority only as the global issuer list `authoritativeSources`. It is not scoped by claim type, predicate, resource, or time window. A verifier may consult that global premise, but the documentation must not present it as a granular contractual delegation.

If a key precommitted for a provider-controlled issuer signs `completed`, the lab may authenticate that fixture issuer and the interaction-bound statement. It must not relabel the statement as neutral outcome evidence or claim a production SaaS capture path that the adapter did not prove.

If a key precommitted for a separately identified issuer signs `completed`, the lab may authenticate that distinct fixture identity. Independence, authority, and any real external acquisition path remain claims that need their own support.

The fixture identities must be read literally:

| Artifact | Signed fixture issuer | What authentication means here | What it does not mean |
| --- | --- | --- | --- |
| payment verification / settlement | `local-recording-facilitator` | that key signed the recording double's envelope | production verification, transfer, or finality |
| HTTP response | `lab-http-capture-adapter` | the harness capture adapter signed its captured response object | provider authorship, remote-origin identity, or TLS-channel attestation |
| deferred job status | `lab-job-state-adapter` | the lab adapter signed the fixture job-state object | independent observation or authority; authority is evaluated separately |
| source statement | `local-provider` or `lab-separate-observer` | the prebound source key signed the statement envelope | truth, independence, or contractual authority |
| verified-payment cancellation | `x402-express-middleware` | the prebound fixture key signed the recorded cancellation observation | a production middleware attestation |

## HTTP and output assumptions

The scenarios deliberately separate several layers:

- an HTTP status describes the request/response boundary;
- JSON Schema describes structural conformance;
- a receipt or settlement event describes the payment boundary;
- a later status describes a deferred job at a point in time;
- a commercial obligation describes what the parties intended to buy.

No layer silently implies the next one.

In particular:

- HTTP `200` is not proof of commercial fulfilment;
- valid JSON is not proof of correctness;
- schema conformance is not proof of usefulness or completeness;
- settlement is not proof that the response body was bound into the payment evidence;
- a successful synchronous response is not proof of later asynchronous success.

The current HTTP signature is an attestation by `lab-http-capture-adapter` about a response object collected inside the local harness. It is not a signature created by the protected handler or provider, and it is not proof of an authenticated remote HTTP/TLS exchange. The verifier requires both the precommitted issuer/key binding and equality between the captured `resourceUrl` and the plan resource before using that artifact for HTTP or schema claims.

The current asynchronous-job artifact is created and signed by `lab-job-state-adapter`. The `accepted-then-async-failure` trust context separately places that fixture issuer in the global `authoritativeSources` list consumed by the job verifier; this is not a predicate-scoped appointment, and the signature alone would not supply even that premise. The verifier also binds its job ID to the job ID in the signed HTTP capture.

## Signed offers and receipts

The x402 signed offer/receipt extension can support claims about the fields it signs. In the inspected implementation, the receipt payload includes payment/resource metadata such as version, network, resource URL, payer, issuance time, and optionally a transaction reference. It does not by itself include a hash of the delivered response body, an output schema, a deferred job identifier, or the full commercial obligation.

Therefore a valid receipt must not be interpreted as a body-integrity or fulfilment attestation unless an additional, explicitly verified binding is present.

When the lab evaluates a response-body binding, it hashes the canonical JSON **value** of the captured body. This is not a hash of raw HTTP bytes, content encoding, transfer framing, or serializer whitespace.

## On-chain non-assumption

The v0.1 `ONCHAIN_SETTLEMENT` verifier always returns `UNKNOWN`. If no confirmation artifact exists, it reports that absence; if one is supplied, it still reports that chain verification is not implemented. Arbitrary JSON stating that a transaction is confirmed is not receipt, confirmation-depth, or finality evidence.

## Validation assumptions

The laboratory treats schema validation and claim evaluation as deterministic for the same:

- canonical input bytes;
- schema version and digest;
- verifier version;
- trust profile;
- allowed algorithm set.

Unknown versions and unsupported algorithms should fail closed at the technical boundary. Missing or insufficient evidence normally yields `UNKNOWN` for the affected claim, not an invented negative conclusion.

For the current x402 adapter, “supported version” means exactly `2.19.0`, not a compatible range.

## Diagnostic trace assumption

`trace.json` is a diagnostic export of local control flow. It is not an evidence artifact, is not signed or covered by the plan/bundle/report commitments, and is not reproduced or authenticated by dossier verification. The current verifier does require the file to exist and parse as JSON as a dossier-shape check; its content is not an input to claim derivation. Claim results derive from the verification plan and evidence bundle, not from the exported trace. Internal recorder events may still be used by the scenario runner to construct an evidence artifact (for example, cancellation); that capture mechanism is distinct from trusting `trace.json` itself.

The public report schema applies a closed compatibility matrix across claim type, status, and reason code. This is a semantic validation boundary, not only a field-shape check. It structurally rejects `OBLIGATION_FULFILLED / PROVEN` and `ONCHAIN_SETTLEMENT / PROVEN` in v0.1.

## Explicit non-assumptions

The initial version does not assume:

- buyer or provider honesty;
- that different hostnames imply different controllers;
- that different keys imply organizational independence;
- that a rail receipt binds service delivery;
- that the HTTP capture signature came from the provider or authenticated a remote origin/channel;
- that the job-state adapter is independent or authoritative merely because it signed an artifact;
- that an external API is correct or stable;
- that all relevant evidence was disclosed;
- that the lab is a regulated payment service, escrow, arbitrator, insurer, or legal expert determiner;
- that a report has authority to move money.

All reports therefore use `economicAction: "NOT_EVALUATED"`.

## Version drift

Upgrading x402, a schema, a verifier, or a canonicalization rule creates a new evidentiary context. Upgrades should include:

1. a pinned dependency change;
2. a review of upstream lifecycle semantics;
3. regenerated golden reports;
4. regression tests for every existing scenario;
5. a documented migration note if interpretation changes.

A report produced under one version should remain readable, but it must not be silently reinterpreted under another.
